Extensions

Extensions plug into Fathom APIs, not Pi’s terminal-app extension API. Pi hands extensions terminal widgets, themes, editors, and keybindings. That does not map cleanly onto a desktop web UI, and we are not on Pi’s agent stack anyway.

Three places to plug in, different jobs. Runtime is what the agent can do — tools, hooks, session state, extra prompt context, runtime events. Desktop UI is how the app looks and feels. Host finds and loads packages — manifests, on/off, reload, permissions, and wiring.

Layer Job Examples
Runtime What the agent can do tools, hooks, session state, extra context, events
Desktop UI How the app looks and drives tool views, panels, message box, layouts, editors, shortcuts
Host Find, load, connect manifests, enable, reload, permissions, wiring

One package can plug into more than one layer. A todos package might add tools and events in the runtime, show a side panel on desktop, and on web only ship the runtime part with no panel.

Module example: todos Todo tools, store, todos_updated events

Backend plugins may add tools, providers, commands, extra prompt context, history trim strategies, resource discovery, tool policy, session search data, and workspace helpers. UI plugins may add command palette items, menus, shortcuts, how a message block looks, how a tool call looks, panels, status items, and settings forms.

Extensions can ship with the app, live in a user folder like ~/.fathom/extensions, or live in the repo under .fathom/extensions. A company install may allow or block the user and repo locations. Two tools or two panels cannot share the same name.

Features we ship should use the same APIs outside plugins use: tools, panels, renderers, commands. That forces the APIs to stay usable and lets optional features turn off. The runtime, loader, host, login path, and base chat UI are not optional plugins.

platform/ Always on: runtime, host bridge, base UI slots, loader, auth builtins/ Same APIs as extensions; our features; can turn off; tool packs via profiles extensions/ User and repo folders; can turn off

Prefer a few named profiles (default, read-only review, immersive) over lots of independent toggles for basic tools. The enable UI should list optional product modules and user extensions. It should not offer “turn off sessions.”

For the first version, extensions are trusted internal code. We do not need a full third-party install and permission system yet. Prefer simple declared UI contributions when they are enough. Do not make the stable plugin API depend on private UI framework objects.

What the spike already does

Look at spikes/desktop-agent. Manifests live under .fathom/extensions/<id>/ with backend and UI entry files. Backend activate can register tools and commands. UI activate can register tool views and replace the message box. The host loads and reloads by generation number and refuses reload while a run is busy. The spike still wires Pi Agent in places — treat that as old prototype code, not the target. Target is our loop plus Fathom registration APIs.

Next we want a real runtime module API and a clear list of desktop UI slots, with the host loader kept outside the runtime package.
