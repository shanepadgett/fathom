Reload

While building an extension, reload has to work every time. We replace the whole Deno worker instead of trying to clear Deno’s module cache in place.

Pi’s coding agent reloads in-process with loader tricks. Deno can run TypeScript, but reloading one entry file does not reliably reload nested imports, and old modules cannot be fully thrown away. A new worker is a clean JavaScript world. Entry files, imports, top-level variables, timers, and registrations all start over from disk.

One worker for the whole engine

There is one worker for the full headless engine, not one worker per extension. The desktop host creates that worker, watches it, replaces it on reload, keeps windows alive, and ignores messages from old workers. Inside the worker: our session runtime, our loop, SQLite, AI Core model and credential code, extension loading, and backend extensions as normal modules.

Loading extensions inside the engine worker keeps the API simple. Tools and hooks are normal functions and objects. We do not need a mini RPC layer per extension.

What reload does

The host asks the current engine to prepare reload. If a run is busy, reload is rejected, or the caller must abort the run and wait — we never cut a run without saying so. The engine saves pending data, marks an aborted run correctly, tells extensions to shut down, and closes SQLite. Then it says it is ready. The host kills the old worker (force-kill if shutdown hangs), bumps a generation number, starts a new worker, scans extension folders again, starts extensions in a fixed order, opens SQLite, restores the open workspace/session/branch/model/tools/settings, sends a full snapshot, and marks the engine ready. The UI only accepts commands for the new generation.

Reload and crash recovery rebuild state the same way. Reload is the clean path. Crash recovery is the same path after a hard stop, plus cleanup for the interrupted run.

Generation numbers

Every message to or from the worker carries a generation number. The host only trusts the current one. A late event from a dead worker cannot change the new UI. Requests that were in flight during reload either fail or wait in the host, by a clear rule. They must never be sent to both workers.

interface EngineEnvelope<T> { generation: number; requestId?: string; payload: T; }

Loading extensions and what survives

Each new worker scans extension folders from scratch. It should report problems without half-starting two copies of the same extension. Start order is fixed. Each extension gets a small scope object that records what it registered. Old scopes die when reload starts; a late callback from an old extension should fail, not touch the new runtime.

Only clear app state survives a worker swap: rows in SQLite, which workspace and session were open, model and thinking settings, which tools were on, extension settings meant to persist, and UI editor state. Global variables, timers, half-finished tool calls, and closures inside old modules are gone. If an extension needs data across reload, it must save that data through our storage APIs. Simple test: if a clean reload loses it, it was stored in the wrong place — unless you meant it to be temporary.

UI reload

Replacing the backend worker does not unload JavaScript already in the desktop web page. Start with declared UI contributions so backend changes show up in the new snapshot without loading extension UI code into the page. If we later allow custom UI code from extensions, true reload means replacing that code too: either reload the whole web page after saving editor state, or put each custom view in an iframe and recreate it. Cache-busting script URLs alone still leave old code in memory.

What automated reload tests must show

Adding an extension makes its features appear without restarting the whole app. Editing the extension entry file, or a file it imports, changes behavior after one reload. Removing the extension removes every contribution. Old handlers, commands, timers, and globals are gone. The open session and branch come back at the same saved point, with model, thinking level, tools, and saved settings restored. Messages from the old generation are ignored. A failed extension start reports an error without breaking SQLite. A stuck shutdown is force-killed and the new engine still starts. Doing this many times does not stack old module copies in one process.
