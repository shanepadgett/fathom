# Fathom architecture

Fathom is a coding harness where every feature is a plugin. It is an Elixir
application: a Phoenix host on the BEAM, rendered by LiveView in a Tauri
window. This document draws one line from the person using the app, through
the person writing a plugin, to the code Fathom itself keeps. Anything not on
this line is a mistake.

## Three people

| Person | What they touch | What they never see |
| --- | --- | --- |
| End user | `Fathom.app`: the workspace, settings, providers, and plugin manager. Enables, disables, configures, and replaces plugins. | Kernel, host, shell. |
| Plugin author | One Mix project generated by `mix fathom.gen.plugin`. Depends on `fathom_sdk` and on definition packages for the contracts it uses or implements. | Kernel, host, shell, release tooling. |
| Fathom maintainer | Everything, including the harness and the bundled plugins. | Nothing. |

## The line

```text
End user
  Fathom.app ── Tauri window ── AppLive (renderer root) ── shell plugin ── slot views (plugins)
                                    │
Plugin author                       │ provide services, contribute to registries
  plugins/<id>/                     ▼
    mix.exs             mod: {X.Application, []}, env: [fathom_plugin: X.Plugin]
    lib/x.ex            the context: public API, often a service contract
    lib/x/plugin.ex     use Fathom.Plugin: requires, provides, config, contributions
    lib/x/application.ex supervision tree ending with {Fathom.Plugin.Publisher, X.Plugin}
    lib/x_web/*.ex      LiveViews contributed to slots
                                    │
SDK (fathom_sdk)                    ▼
  Fathom.Plugin, Publisher, Manifest     Fathom.Service, Fathom.Registry, Fathom.Events
  Fathom.Storage, Environment, KernelControl (contracts)   Fathom.UI (slots, controls, slot_view)
  Fathom.HTTP, Fathom.SSE                mix fathom.gen.plugin
                                    │
Harness (apps/fathom and apps/desktop; not replaceable)
  kernel      Fathom.Kernel + Graph, Catalog, Runner, Config, Desired
  registries  Fathom.Services (unique) and Fathom.Contributions (duplicate), Elixir Registry
  host        Fathom.Host.Plugin (harness services and slots), Environment, Launch
  renderer    FathomWeb.AppLive, the recovery panel, the root layout and appearance hook
  shell       apps/desktop: Tauri window, menu, host process lifecycle, browser tab webviews
                                    │
Runtime                             ▼
  BEAM (OTP applications, processes, ports)   │   WebKit page (LiveView client)
```

## What is a plugin and what is harness

The test: if a user could reasonably want it different, it is a plugin. The
harness is only what a plugin needs in order to exist at all.

| Plugin (replaceable) | Harness (fixed) | Why fixed |
| --- | --- | --- |
| storage, credentials, llm, provider-* | kernel | Lifecycle rules must be the same for every plugin or nothing composes. |
| workspace shell, settings pages, plugin manager | registries, publisher | Ownership of registrations must end with the owner, for every plugin. |
| sessions, tools, approvals, agent loop, conversation UI, composer (roadmap) | renderer root and recovery panel | Recovery must survive removal of every UI plugin. |
| theme selection, commands, editors (later) | shell, launch handshake | The process must open a window before any plugin runs. |

The harness has no feature behavior. If harness code starts knowing about
models, sessions, or providers, it belongs in a plugin.

## How a plugin runs

A plugin is an OTP application. Its manifest (`use Fathom.Plugin`) declares
an id, the tokens it requires and provides, and a `NimbleOptions` config
schema. The host compiles bundled plugins as path dependencies with
`runtime: false`, so OTP loads them but never starts them; the kernel does.

```text
Kernel.init
  Catalog.manifests(config :fathom, :plugins)      load apps, read app env :fathom_plugin
  Desired.read(home/plugins.json)                   enabled + config per id
settle (repeat until stable)
  Graph.to_stop       running but disabled or missing a token → stop, dependents first
  Graph.next_start    enabled, every required token available → Runner.start
Runner.start
  Application.put_env(app, :fathom_config, cast config)
  Application.ensure_all_started(app)               the plugin's tree starts...
    ...ending with Publisher.init                   registers services and contributions
  Process.monitor(application master)               a crash beyond restart → :failed
```

Tokens are modules. A service token (`use Fathom.Service`) is a contract:
a behaviour plus client functions that dispatch with `Fathom.Service.call/3`.
A registry token (`use Fathom.Registry`) collects keyed entries. The
publisher registers both in Elixir `Registry` tables owned by the host, so a
plugin's registrations end with its publisher process: on stop, on crash, or
on restart, with no cleanup code anywhere.

Swappable capabilities are split three ways. A **definition package** is a
plain library: the contract module, its structs, registry tokens, provider
behaviours, and pure helpers. It runs no processes and the kernel never sees
it. A **provider** plugin implements the contract and lists it in
`provides:`. A **consumer** plugin lists it in `requires:`. Both depend on the
definition like any library and never on each other, so a replacement
provider drops in by providing the same token while the original is disabled.

| Definition (`packages/`) | Bundled provider | Consumers |
| --- | --- | --- |
| `fathom_sdk`: `Fathom.Storage`, `Fathom.Environment`, `Fathom.KernelControl`, `Fathom.Folder`, `Fathom.Shell`, UI slots | `storage-sqlite`; the harness for the rest | counter; every plugin with UI |
| `fathom_credentials`: `FathomCredentials`, `Credential`, `LoginFlow`, `Logins`, `OAuth`, `DeviceCode` | `credentials-local` | llm-router; provider plugins contribute login flows |
| `fathom_llm`: `FathomLlm`, `Provider`, `Providers`, `Protocols.*` | `llm-router` | agent; provider plugins contribute providers |
| `fathom_agent`: `FathomAgent`, `Tool`, `Tools` | `agent` | browser (Send to agent); coding-tools contributes tools |

## Seams

Each seam is a module boundary where the next piece of work plugs in without
reshaping the rest.

| Seam | Today | Next |
| --- | --- | --- |
| `Fathom.Kernel.Runner` | Starts a plugin's application on the host node. | A peer-node runner for plugins with their own Hex deps or NIFs, chosen per manifest. |
| `Fathom.Service.call/3` | Applies the provider module locally. | Dispatches with `:erpc` when the provider runs on a peer. Contracts pass data and pids, never functions, so they already work across nodes. |
| `Fathom.Kernel.Catalog` | Bundled plugin apps listed in host config. Local plugins arrive through `Fathom.Kernel.sync_local/1`. | Plugins installed from Hex or git, built by the same builder. |
| `Fathom.Kernel.Graph` | Pure decisions over plugin records. | Richer policies (ordering hints, optional requirements) without touching effects. |
| `Fathom.UI.slot_view/1` | Each contribution is a nested LiveView, its own process. | Slot composition settings that pick among contributions. |
| `Fathom.Plugin.Manifest` | id, requires, provides, config, enabled. | Isolation level, contract versions. |

## Plugin UI

Plugin UI is LiveView. A contribution names a LiveView module; the shell
renders it nested with `slot_view/1`, so every plugin view is its own
process and a crash in one view never takes down the shell. Views call
contexts directly and subscribe with `Fathom.Events` or a context's
`subscribe/0`. Controls come from `Fathom.UI.Components`; the theme lives in
`packages/fathom_sdk/priv/css`. Icons are Phosphor classes written in full
(`"ph-gear"`) so the stylesheet build finds them.

JavaScript is limited to the harness and to colocated hooks in bundled
plugins. The harness has the LiveView client and the `FathomAppearance` hook
behind `appearance_control/1`, because appearance is browser-local. A bundled
plugin that needs a hook adds `compilers: [:phoenix_live_view] ++
Mix.compilers()` to its `mix.exs`; `mix fathom.plugin_hooks` collects every
plugin's colocated hooks into `assets/js/plugin_hooks.js` for `app.js`, so
the host never names a plugin. Local plugins cannot ship hooks yet.

Hooks import JavaScript libraries the host ships, as it ships Jason to
Elixir plugins: `apps/fathom/assets/package.json` (CodeMirror today),
installed by `mix setup` and resolved through esbuild's `NODE_PATH`.

### Docks and the browser

`Fathom.UI.Docks` contributions get a header button; the workspace shell
slides the dock in from the right and keeps its view mounted while closed.
`Fathom.UI.Docks.open/1` opens one from code.

The `browser` plugin is a dock. Its tab state lives in `FathomBrowser.Tabs`;
each tab with a page is a native webview that the Tauri shell lays over the
dock's viewport (`apps/desktop/src-tauri/src/browser.rs`, using Tauri's
`unstable` multi-webview API). The view's hook calls the shell's one command,
`browser`, with which tab shows and where, every frame the layout moves; the
shell sends page loads, titles, and new-window requests back as DOM events.
Only the Fathom page may call `browser` (`capabilities/host-page.json`). In a
plain browser tab (`mise run dev:browser`) the dock shows that it needs the
desktop app.

The shell stays generic: the page can give a script that runs in every new
tab before the tab's own scripts, run more script in a tab, and listen to one
tab. Tab pages may call only `browser_message`
(`capabilities/browser-tabs.json`), and the shell passes a message on only
from the tab the page is listening to.

Annotating is built on that. The browser plugin's `priv/annotator.js` runs in
every tab and does nothing until the dock starts it in the active tab. Then
hovering outlines elements, a click opens a panel in a shadow root for a note
and live style edits, and Add sends the element's selector, HTML, box, style
changes, and source location (Phoenix `debug_heex_annotations`, React,
Svelte, Vue development builds) to `FathomBrowser.Annotations`, which numbers
the note. The dock lists the notes and copies them as Markdown with
`FathomBrowser.annotations_prompt/0`; pins on the page follow the list.
Everything in a note but the comment and style values comes from the page,
so it is untrusted input to an agent.

## Agent and editor

`FathomLlm.stream/3` takes a conversation: a system prompt, messages, and
tools. It streams text, reasoning summaries, and finished tool calls to
`reply_to` and returns the whole reply. Assistant messages keep the
provider's own record (`native`); the Responses protocol replays it to the
same model, which keeps OpenAI's encrypted reasoning with `store: false`, and
rebuilds messages from other models from `content`. With a Claude sign-in,
tools go out under Claude Code's names.

```text
Chat page ── FathomAgent ──▶ Session (one GenServer per session)
                               │ record, partial reply, session file
                               └─▶ Loop (task): FathomLlm.stream ──▶ provider
                                     └─▶ tools in FathomAgent.Tools ──▶ coding-tools
```

The `agent` plugin provides `FathomAgent` and owns the `FathomAgent.Tools`
registry. A session's record is the conversation plus notices, saved to
`<home>/sessions/<id>.json` after every entry; a run interrupted by a stop or
a restart gets error results for its unanswered calls, so the conversation
stays valid. The session coalesces stream fragments and numbers its events
(`seq`), so a view that subscribes and then takes a snapshot skips
duplicates. Stopping kills the loop task; the bash tool's watcher then kills
the command's process tree.

`coding-tools` contributes `read`, `write`, `edit`, and `bash` with Pi's
argument shapes and limits. Commands run in the login shell with
`Fathom.Shell.env/0`: the terminal's `PATH`, without Fathom's own `RELEASE_*`,
Erlang, and launch variables. Tools run without approval.

`Fathom.Folder` is the folder the person works in: chats start there and the
editor shows it. `Fathom.Folder.open_file/2` asks whatever shows files to
show one, so tool cards link to the editor without knowing it exists. Paths
are real paths (`/tmp` is `/private/tmp` on macOS), because language servers
report real paths.

The `editor` plugin is a dock: the folder's tree, tabs in
`FathomEditor.Tabs` (with unsaved text, so it survives the dock unmounting),
and one CodeMirror view per open file in a colocated hook. A folder watcher
reloads clean files an agent changed and asks before replacing unsaved text.
Language servers run per editor view over stdio (`FathomEditor.LanguageServer`),
relayed through the LiveView to `@codemirror/lsp-client`. Elixir uses Expert,
downloaded once into `<home>/tools` and checked by SHA-256; other languages
use a server on the login shell's `PATH`. Fathom answers the server requests
CodeMirror's client does not implement and sends `didSave` and
`didChangeWatchedFiles`, which Expert needs to rebuild.

## Local plugins

Anyone can write a plugin for the shipped app. A local plugin is an ordinary
Mix project in `~/.fathom/plugins/<name>/`; Settings › Plugins › New plugin
generates one. It may depend on Hex packages, including precompiled NIFs.

```text
Fathom.Plugins.Local          builds at launch, on New plugin, and on Reload; between
                              builds, lists plugins whose files changed
  Builder (own OS process)    bin/fathom eval in a release, elixir in development
    workspace mix.exs         local plugins as path deps; Hex packages the host ships
                              pinned to its versions; stand-ins for Fathom's own apps
    deps.get, compile         only what the host does not ship; failures stay per plugin
    Tailwind                  plugin classes against the SDK theme -> /plugins.css
  Loader                      load changed modules in place, consolidate protocols again
  Kernel.sync_local/1         add, remove, retry failed, mark running plugins stale
  Kernel.restart_stale/0      after a Reload: restart what was marked stale
```

Fathom does not build while files change, because an editor or agent may
still be writing. The header shows "N plugins changed · Reload"; Reload
builds, replaces code that a running plugin can take in place (any module
except its manifest and application module) and re-renders views with their
state through `Fathom.UI.CodeReload`, then restarts plugins whose manifest,
contributions, application spec, or application module changed. A failed build leaves the previous build
running. Mix and Hex live under `~/.fathom/mix`, compiled code under
`~/.fathom/build`, and Tailwind, downloaded on first use and checked by
SHA-256, under `~/.fathom/tools`.

## Development loop

`mise run dev` builds the Tauri shell, which starts `mix phx.server` with
`FATHOM_DESKTOP=1`. Phoenix's code reloader lists the SDK and every bundled
plugin in `reloadable_apps`, and LiveReload's `notify` re-renders LiveViews
in place, keeping their state. Saving a plugin file reloads its modules in
the running app; running processes pick up the new code on their next call.
A bundled plugin whose manifest or supervision tree changed needs **Restart**
in Settings › Plugins. Local plugins work the same in development as in the
shipped app. `mise run dev:browser` runs the same host in IEx, which can call
any context directly.

## Repository

```text
apps/fathom/          The host: kernel, registries, endpoint, renderer root. mix phx.new
apps/desktop/         The Tauri shell. cargo tauri init
packages/fathom_sdk/  The SDK and its generators. mix new
packages/<name>/      Definition packages: contracts other plugins build on. mix new
plugins/<id>/         Bundled plugins. Each is exactly what a third party would write.
examples/counter/     The plugin the guide walks through. Starts disabled.
design/               Visual reference. Read, never reorganized.
docs/                 This file, guides/, standards/, plans/
```

Dependency direction, enforced by review:

```text
plugins ──▶ fathom_sdk ◀── apps/fathom ◀── apps/desktop (process, not code)
plugins ──▶ definition packages ──▶ fathom_sdk
nothing ──▶ plugins (the host lists them in config; the kernel never names one)
```
